# Orbit 1.0 product plan

This plan defines what must be true before Orbit becomes public and publishes
`v1.0.0`. Passing CI or producing release binaries is necessary but not
sufficient: a new user must be able to understand, start, diagnose, and stop an
environment without learning Orbit's internal architecture.

## Release approval gate

The source repository may be public during product hardening. Creation or push
of a `v1.0.0` tag and publication of the stable GitHub Release remain manual
approval gates. Automation and implementation work must stop before those
actions until Logan has reviewed the complete release candidate and explicitly
approved the release. A green test suite, completed checklist, or available
artifact is not release authorization.

## Product promise

Orbit makes a mixed local-development environment feel like one application.
It coordinates host processes and containers, starts them in dependency order,
checks health, keeps useful logs, and gives the developer one place to see and
control the result.

The primary user is a developer joining or working in an existing multi-service
project. A maintainer defines the shared environment once; other developers
should normally need only:

```text
orbit init
orbit up
orbit status
orbit logs <resource>
orbit down
```

## 1.0 commitments

- Host services and containers can share one dependency graph and lifecycle.
- Git-backed environments can be synced and switched predictably.
- The CLI and dashboard expose the same state and safety rules.
- Failures identify the affected resource, the cause, and a concrete next step.
- Optional workflows are absent from the experience until explicitly enabled.
- The `orbit.cli.v1` JSON envelope remains compatible throughout Orbit 1.x.
- macOS and Linux are supported and release-blocking.
- Windows is Beta: binaries and smoke coverage are provided, with limitations
  documented; non-safety Windows defects do not block 1.0.
- SQL Server Database Projects are an official, optional workflow.
- Orbit never installs project runtimes or package dependencies implicitly.

## Non-goals for 1.0

- Replacing Docker Compose, language version managers, or package managers.
- Treating unrelated database workflows as one provider abstraction.
- Managing production deployments.
- Installing or modifying dependencies inside a user's project without an
  explicit command.
- Hiding configuration mistakes behind runtime guessing.
- Guaranteeing full Windows parity while support remains Beta.

## UX invariants

These are release requirements, not design aspirations.

### Ask only for proven requirements

`orbit init` never treats an arbitrary current directory as a workspace.
Distribution defaults and self-contained environments require no setup
questions. A project workspace appears only after the selected environment
proves that local project files are required.

### Show only relevant concepts

A Python-only environment reports Python, not Node, pnpm, .NET, or SQL Server.
An environment without a tunnel or SQL Server workflow does not show skipped
checks, empty navigation, or setup prompts for those features.

### One primary next action

Successful setup ends with `orbit up`. Advanced choices such as
`orbit up --infra` remain discoverable in help, not presented as competing
first steps.

### Detect; do not silently mutate

Orbit may detect a missing runtime, package install, port conflict, or optional
workflow. It reports what it found and gives a copyable remedy. It does not
install a runtime, run a package manager, or rewrite a project automatically.

### Explain failures in user terms

Every actionable failure should answer:

1. What could not complete?
2. Which service or container is affected?
3. What evidence did Orbit observe?
4. What should the user do next?

Raw process errors may be retained as details, but must not be the only
explanation.

### Keep destructive behavior explicit

Operations that discard data, allow data-loss schema changes, or remove local
state require a specific command and confirmation. CLI, JSON, dashboard, and
agent guidance must agree on the risk.

### Prefer one source of truth

The same decision should not require unrelated settings, environment variables,
and sidecar files. Per-machine settings hold machine facts; the environment
file holds shared project intent; secrets remain external.

## Minimum user journeys

Each journey needs an automated test where practical and a clean-machine
release check where platform behavior matters.

### First run

1. Install Orbit.
2. Run `orbit init` in an empty directory or existing workspace.
3. Sync and select the default environment.
4. See checks only for that environment.
5. Run `orbit up`.
6. Open the demo service and dashboard.
7. Run the mini-shop smoke path to get from 0 到可展示 demo：
   - 一次完成「開始 demo 一輪」與「核對可 demo 條件」。
   - 能夠在同一頁面做一次失敗回歸（付款失敗 / 庫存不足）並看見可執行建議。
8. Run `orbit down`.

### Join an existing team

1. Install Orbit.
2. Sync a team environment repository.
3. Select an environment.
4. See missing runtimes or project dependencies with exact remedies.
5. Start the whole environment without manually ordering resources.

### Daily recovery

1. Identify a degraded service from `status` or the dashboard.
2. Read its logs without finding an internal daemon log first.
3. Apply the suggested remedy.
4. Restart only the affected resource and observe recovery.

### Environment switch

1. Preview available environments.
2. Switch with one command.
3. Reject an invalid target before stopping or changing the current environment.
4. Understand what remains running and what changes.
5. See newly required host tools before startup fails.

### SQL Server project workflow

1. A non-SQL environment has no SQL Server concepts.
2. An explicitly configured environment shows the SQL Server surface.
3. Doctor reports only that workflow's missing tools and credentials.
4. Diff is safe and readable.
5. Publish preserves data by default.
6. Reset and forced publish require explicit confirmation.

### Upgrade and removal

1. See the installed version and available update.
2. Upgrade without losing environments or settings.
3. Roll back using a documented release artifact.
4. Remove Orbit while clearly choosing whether local configuration and data
   remain.

## Workstreams

### 1. First-use and daily CLI

- Validate `init --yes` from a clean directory.
- Remove irrelevant Doctor checks and feature prompts.
- Detect runtimes from selected service commands and project version files.
- Detect missing package installs without running package managers.
- Make human errors and JSON recommended actions converge.
- Review command discovery so internal/advanced commands do not dominate help.

### 2. Optional SQL Server workflow

- Replace implicit name/image detection with explicit `sqlserver` config.
- Keep `orbit db`, while naming SQL Server in help, output, and dashboard.
- Co-locate target and project declarations in the environment.
- Remove SQL Server assumptions from core validation and settings.
- Publish a minimal public SQL project example.
- Provide documentation-only migration from pre-1.0 configuration.

See [SQL Server workflow design](sqlserver-workflow-design.md).

### 3. Configuration and lifecycle stability

- Finalize schema versioning and unknown/deprecated field behavior.
- Define machine settings, shared environment, and secret boundaries.
- Exercise daemon crash, stale state, port collision, sleep/resume, and Docker
  restart recovery.
- Verify simultaneous workspaces and namespace isolation.
- Freeze the JSON compatibility policy for 1.x.

### 4. Installation and platforms

- Test installation, update, rollback, and removal on supported platforms.
- Add Linux E2E and Windows Beta smoke coverage.
- Make shell, path, permission, and signal assumptions explicit.
- Test release artifacts, checksums, and reported versions.

### 5. Security and public release

- Audit local API bind and authorization boundaries.
- Prove secrets are absent from logs, status, JSON, and release artifacts.
- Add `SECURITY.md`, SBOM, and release provenance.
- Complete license and third-party asset review.
- Validate anonymous clone, install, release download, and demo sync only after
  repositories become public.

## Release gates

`v1.0.0` is allowed only when:

- Demo strategy evidence is current: the mini-shop demo is the default first-class showcase and remains intentionally simple enough for first-run onboarding, with explicit failure recovery path and optional mixed-technology story kept out of critical path.
- Every minimum user journey has current evidence.
- macOS and Linux test matrices pass from a clean user context.
- Windows Beta limitations and smoke results are published.
- No optional feature appears in an environment that did not enable it.
- No supported journey requires editing `settings.json` directly.
- Human failures and JSON recommended actions provide the same remedy.
- The SQL Server workflow is explicit and its destructive paths are verified.
- Install, update, rollback, and removal are documented and tested.
- CI, vulnerability, secret, license, SBOM, provenance, and release checks pass.
- Public-only anonymous checks pass before the immutable `v1.0.0` tag is made.

## Current evidence and known gaps

The private `v0.0.3` rehearsal proved clean-history migration, release assets,
checksums, the Python/Redis demo, and the private installation path.

The first 1.0 UX audit found and began addressing:

- `orbit init --yes` failed in a clean directory, and the interactive path
  later persisted that arbitrary directory as a workspace even when the demo
  did not use it.
- Doctor checked global .NET and pnpm assumptions while failing to check the
  Python runtime required by the selected demo.
- Doctor exposed an irrelevant "DB workflow skipped" concept.
- Setup presented infrastructure-only startup alongside the primary next step.

These findings demonstrate why release readiness is judged by user journeys,
not by the number of existing features or passing unit tests.

The next team-join audit found a second connected failure path:

- Doctor treated an installed Python runtime as complete project readiness even
  when the selected service's `requirements.txt` was unsatisfied.
- The daemon replaced a deterministic process exit and useful application
  evidence with `context canceled` in durable status.
- Logs then recommended a restart that could not change the missing dependency.

The v0.0.15 hardening slice addresses that path as one product behavior:
pre-start dependency readiness, durable failure evidence, and a cause-specific
setup-then-targeted-restart action.

The next lifecycle audit connected two apparently different failures to lost
resource ownership:

- A targeted host-service restart could signal the same process group from two
  concurrent paths, then misreport Orbit's still-exiting process as an external
  port conflict.
- After an abrupt daemon exit, live namespaced containers and persisted host
  processes could be shown as stopped; following the normal `orbit up` action
  then collided with Orbit's own ports.

The v0.0.16 hardening slice treats both as one product invariant: ordinary
restart and startup reconcile Orbit-owned resources before classifying an
external conflict. Users should never need process-group, stale-socket, PID, or
Docker-namespace knowledge to recover resources Orbit already owns.
